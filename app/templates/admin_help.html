Dashboard README

Maintained: 2026-06-18 — features and status below reflect the current build.

A small internal portal that shows dealers across the UK, Sweden and Norway when Ducati bikes are likely to be available. The admin uploads the plan workbook, the orders export, and (twice a day) the allocations file.

The site opens directly on the general availability grid — the country-wide view every dealer sees, no password required. A Log in item in the top nav takes you to the password page: the admin password unlocks the admin tools, and a dealer's personal password shows that dealer their own committed orders on top of the shared grid (via the My orders nav link). Logging out returns you to the public availability view.

What you can do today

Upload data Live

Admin → Upload takes three xlsx files independently. Each has Upload new / Reuse last upload radios so you can refresh just one side without re-uploading the others.

  • Plan workbook — typically refreshed monthly. Each upload replaces the plan and wipes the allocations table (a new plan = new accounting period).
  • Orders export — open orders only. Each upload replaces the orders table.
  • Allocations — bikes that have been allocated. A bike's life is forecast → open order → allocated; once allocated it drops off the orders sheet and appears here, so allocations and open orders are the same bikes at different stages and are added together, never double-counted. Cumulative across uploads within an accounting period, deduped by order number. Twice-a-day cadence is expected. Two file shapes are accepted:
    • Single-period file — filename pattern Allocations DD.MM.YY am|pm.xlsx. The date is read from the filename.
    • Master workbook — one sheet per period, sheet names like 22.05.26 pm. The system walks every dated sheet chronologically and ingests each as its own report. Re-uploading a master is safe: dedup-by-order-number keeps the data clean.

    Replace all existing allocations — a tick-box on the allocations upload. Leave it off for the normal append behaviour. Tick it to clear the allocations table first and rebuild purely from this file — handy for a clean reset (e.g. dropping stale data) without re-uploading the plan.

Availability math Live

Accounting month (which months the grid starts from)

The 12-month window doesn't blindly start at today's calendar month — it starts at the accounting month, the month the loaded figures belong to. This matters because allocations are consumed from the forecast starting at the first column: if the window jumped forward the moment the calendar ticked over (say into July) while the data still reflected June, June's allocations would be pushed onto July's forecast and every model would read a month late.

The accounting month is auto-detected from the allocation file's own dates (the sheet/filename dates like 12.06.26). So a June allocation master keeps the figures anchored on June until you roll the period forward — which happens automatically when you upload July's allocations, or the moment you upload a new plan (which wipes allocations to start fresh). The current accounting month is shown at the top of the Forecast view. To force a different month, use Admin → Upload → Accounting month to pin it; a manual pin is cleared automatically on the next plan upload.

For each (model, month) cell, start from the raw monthly position:

raw[month] = forecast[month]
           − allocated[month]     (off the front of the forecast)
           − committed[month]     (open orders FIFO, then overflow)

Allocations come off first: walk months chronologically and subtract from each month's forecast until the allocations count is exhausted; excess spills to the next month. Then committed orders (Demo / Courtesy / End-customer-status=Yes) fill remaining capacity FIFO by order creation date. Overflow piles onto the last month.

Roll-forward. Bikes forecast but not taken in a month don't vanish at month-end — they carry into later months. So the figure that drives the traffic light is the running total of raw from the first month up to that month, not the month on its own. A model whose forecast runs out mid-window keeps showing availability (rather than going red) for as long as unsold stock remains. Because allocations and orders fill earliest-first, the running total only goes negative when a model is genuinely overcommitted overall — which is what a red dot then signals.

No double-counting. Allocated and committed are the same bikes at different stages (see Upload → Allocations). If a feed-timing gap leaves an order showing in both feeds, the allocation wins and the order is skipped, so the bike is subtracted once, not twice.

Hover any cell for a per-month breakdown — it shows both the rolled-forward figure and the raw monthly forecast − allocated − committed. The admin Forecast view also lets you click any row for a full per-model "story": material prefixes feeding in, 12-month totals, allocations broken down by country, committed orders broken down by type, and a numeric per-month table with a Roll-fwd column. Dealers don't see the story panel.

Traffic-light dots

Driven by the rolled-forward (cumulative) available figure:

  •   ≥ 10 available — comfortably open.
  •   1–9 available — limited.
  •   0 or negative — fully booked or overcommitted.

Material → plan-model mapping Live

Orders join to plan rows by the leading token of each order's Material column (e.g. MSV4S → MTS V4 S / MTS V4 S MTO). Unmapped prefixes are excluded from dealer availability until you assign them — this applies to both orders and allocations. Unmapped allocation prefixes used to be dropped silently; now they raise an "N allocation(s) couldn't be matched" banner and show with an Allocations count (amber when unmapped) on the Mapping page. The "N order(s)/allocation(s) couldn't be matched" banners appear on the admin Forecast view only — they're hidden from the dealer-facing view (and from the admin Dealer view preview) so dealers never see internal mapping gaps.

Auto-suggest: on every import, the dashboard scans unmapped prefixes and proposes a mapping by matching the bike's super-model + model name against the plan's. Suggestions appear inline on the Mapping page with Accept / Reject buttons and an Accept all N suggestions shortcut at the top.

  • Matching does case normalization, expands abbreviations (Multistrada ↔ MTS, Streetfighter ↔ SF, Pikes Peak → PP, etc.), and runs four tiers: exact match, model-only exact, token-set inclusion (prefers the most-specific plan whose tokens are fully contained in the bike's or vice versa — catches HYM SP ↔ Hypermotard V2 SP), then contiguous substring as a final fallback for cases like SFV4S3G.
  • Reject suppresses re-suggestion on future imports for that prefix.
  • Some genuine model renames (e.g. plan says Cross 450 but Ducati now calls it Desmo450 MX) will never auto-match — those need a one-time manual mapping. They stick once you save them.
  • Auto-save: changing the plan-model or status dropdown saves immediately and flashes the row green ("✓ Saved"). No page reload. The Save button still works as a fallback if JS fails.
  • Duplicate warning: if more than one material prefix maps to the same plan model, a banner at the top of the Mapping page lists them — usually a sign the matcher picked too generic. Re-point each prefix to its more-specific plan model.
  • Danger zone at the bottom of the Mapping page lets you wipe all mappings (with a backup) and re-run auto-suggest from scratch — useful for testing the suggester.

Embargoes Live

Admin → Embargoes hides selected models from every dealer's view. Tick rows in the table (↑/↓ to navigate, Space to toggle), then use Assign embargo date, Embargo all selected, or Unembargo all selected.

Dealers Live

Admin → Dealers manages per-dealer passwords. Each dealer is bound to a country (UK / SWE / NOR) and a dealer code — the code is what makes their own committed orders show on their page. The admin password and the Months shown to dealers control (1–12) live at the bottom.

The months-visible setting only affects how many column months dealers see on their grid; the forecast math and the "Soonest" calculation always look ahead a full 12 months regardless. Useful when you want to keep dealers focused on the near term without changing the underlying numbers.

Forecast vs Dealer view Live

The admin nav has two read-only views of the availability grid:

  • Forecast — your analytical view. All 12 months, plus the per-row "story" drill-down on row-click. Use this to investigate why a number is what it is.
  • Dealer view — mirrors exactly what a dealer sees: truncated to the months-visible setting, no story panel. Use this to spot-check before a dealer logs in.

Feedback inbox Live

Every page has a 💬 Feedback button bottom-right. Dealers and the admin can use it to send a short message; the current page URL is captured automatically so context isn't lost.

Read submissions at Admin → Feedback. Default view is open items only; toggle to All to see resolved ones. Each row can be marked resolved, reopened, or deleted. Submitter is tagged as admin, dealer:<name>, or anonymous if neither session was active.

Notifications on the admin home Live

  • Embargo may be over — a model is currently embargoed but has open orders against it. Click Lift embargo to make it visible to dealers again.
  • New bikes — plan models that appeared in the latest upload but weren't in the previous one. Embargo to hide while they're being prepared, or Dismiss to mark reviewed.

Automated allocations ingest In progress

Endpoint POST /api/allocations/ingest accepts an xlsx upload from an email-to-webhook service (recommended: CloudMailin) so the twice-a-day Outlook allocations email can flow straight into the dashboard. Auth via X-API-Key header against an env var.

Setup still required: the ALLOCATIONS_INGEST_KEY env var has to be added on Vercel, then CloudMailin + an Outlook rule configured. See docs/allocations-email-ingest.md in the repo for step-by-step.

Weekly / daily routine

  1. Twice a day: allocations file uploaded (manually for now, automated soon via CloudMailin).
  2. Weekly: latest orders export to Admin → Upload. Reuse the plan and allocations.
  3. Monthly: new plan workbook. This wipes allocations to start the period fresh.
  4. After any upload: open the admin home and resolve any notifications. If new material prefixes appeared, head to Mapping and accept/reject the auto-suggestions.
  5. Spot-check via Dealer view before the next dealer logs in.

Source data shape

  • Plan workbook — the parser reads the Sell In block of the DUK_26 / DUK_27 sheets (column layout auto-detected). Other blocks (Sell Out, Dealer Inventory, Shipment) are ignored.
  • Orders export — Export sheet, filtered to Order Status Group = Open and to country UK / SWE / NOR (UNITED KINGDOM, CHANNEL ISLANDS, IRELAND all bucket as UK; SWEDEN → SWE; NORWAY → NOR). The Material column's leading token is the join key.
  • Allocations — like the orders Export sheet but with a leading row-ID column and interleaved blank rows. Filename should match Allocations DD.MM.YY (am|pm).xlsx so the report date is read automatically; an inline date-override field is available if not. Every allocation row is counted regardless of its country value — unlike orders, allocations are not filtered to UK/SWE/NOR (the sheet's country column is unreliable, sometimes carrying a stray code instead of a country). The story panel buckets UK/SWE/NOR and lumps anything else under Other.
  • Allocation sheets aren't a fixed shape, so each is parsed defensively: columns are matched by header name when a header row exists (robust to reordering or missing columns), and by position as a fallback when a sheet has no header. Any sheet that's non-standard — no header, or no Material column so its rows can't be mapped — raises a warning on upload (e.g. "'09.06 am': no 'Material' column — 6 row(s) couldn't be mapped and were skipped") rather than silently undercounting. If you see those, ask the sheet's author to use a consistent layout with a header row and a Material column.
  • Customer / dealer columns — the customer-name column is discarded at parse time for data-protection reasons. Dealer-code is used to filter the per-dealer "Your committed orders" panel.

Troubleshooting

  • Dealer sees stale data — re-upload via Admin → Upload (you can reuse the side that hasn't changed).
  • An allocation isn't showing up in the math — its material prefix is probably unmapped. Visit Mapping; accept its auto-suggestion or assign manually.
  • "Allocations file is older than current snapshot" — you uploaded an earlier-dated file by accident, or the filename's date is wrong. Either upload the correct file or use the inline date-override field.
  • Forgot the admin password — open the Supabase project's SQL editor and run: UPDATE settings SET value='new-password' WHERE key='admin_password';
  • Clean reset — Supabase SQL editor: TRUNCATE plan, orders, allocations, allocation_reports; then re-upload. Dealers, embargoes and mapping stay intact.
  • Debug the auto-suggester — open {{ request.url_root }}dashboard/admin/mapping/dump for a plain-text dump of every prefix, its current/proposed mapping, the bike super/model from orders, and a list of every plan_super/plan_model pair.
  • Auto-save isn't flashing green — open the browser console (F12). The JS logs an explicit error if the form-association lookup fails. The Save button still works as a fallback; submit manually until the underlying issue is sorted.
